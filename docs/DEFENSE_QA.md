# 答辩问答预案（17 题）

所有回答基于真实代码与测试状态。原则：已验证的直接答，未验证的给诚实表述。

**Q1. 为什么选择这个题目？**
长时间桌面使用场景普遍，用户难以持续自我观察姿态。市面上简单阈值方案容易误报打扰。我们想做一个诚实、不打扰、隐私可控的本地工具——工程上有真实难点（个体差异、时序判断、缺失数据处理），适合作为竞赛项目完整落地。

**Q2. 与普通坐姿检测软件有什么区别？**
三点已实现的差异：一，时序状态机——连续 30 秒偏离才算事件，单帧不报警；二，提醒管理——300 秒冷却、120 秒延后、静音与反馈闭环；三，诚实语义——关键点缺失显示"无法判断"，绝不补假值。个人基线是第四个方向，已实现、效果待验证，我们如实标注。

**Q3. 为什么选 MediaPipe Pose 而不是自研模型？**
竞赛周期内自研并验证一个关键点模型不现实。MediaPipe Pose 是成熟的开源模型（Apache-2.0，模型有公开模型卡），33 点带 visibility 置信度，CPU 可实时。我们的工作量在模型之上的特征工程、时序判断、提醒管理、产品与验证体系——这才是项目本体。模型文件 SHA-256 已校验并固化在构建脚本里。

**Q4. 关键点丢失或被遮挡时怎么处理？**
三个层次：单特征——必要关键点 visibility < 0.5 则该特征为 None，按特征独立判定（髋部出画只影响躯干倾角）；单帧——有效率 < 0.5 整帧判 LOW_VISIBILITY，状态机走 UNKNOWN 旁路，**不计为异常也不计为正常**；恢复后——质量恢复自动回到正常判断链。有 12 项特征测试 + 15 项状态机测试覆盖。

**Q5. 什么叫"坐姿不端正"？判据是什么？**
不是主观描述，是明确的可计算量：平滑后的综合偏离量 ≥ 2.0（退出阈值 1.7，滞回防抖）。偏离量两种模式：未校准时为几何偏离量——躯干倾角超过 10° 的部分、肩部倾角超过 5° 的部分、头部前倾比绝对值，三项折算（0–10 量表）取均值，大白话就是"躯干明显前倾 / 肩膀明显歪斜 / 头明显前伸"；校准后则是各特征 |z 分数| 的均值，即偏离本人端正基线约 2 个标准差。单帧达到不算，要 30 帧滑窗平滑后仍超标并连续保持 30 秒，才记为一次"持续坐姿不端正"事件。定义为代码实现（strategies.py / baseline_manager.py），不是 PPT 修辞。

**Q6. 如何避免短暂动作造成误报？**
三道闸：30 帧滑窗平滑抹掉单帧噪声；偏离量须连续保持 30 秒（sustain_sec）才记事件；进出阈值滞回（2.0 进 / 1.7 出）防止边界抖动。低头捡笔几秒的动作不会触发。参数在设置页可调，默认值标注为待标定初值。

**Q7. 个性化基线实际实现到什么程度？**
已实现：校准页 30 秒主动采样，过滤低质量帧，统计均值/标准差，落库；判定时用 z 分数（ε=1e-3 防除零，低方差特征改用绝对偏差归一化）；未校准时明示"默认规则模式"，不伪装个性化；有 15 项单元测试和 1 条真实校准记录（59 样本）。未验证：它对误报率的改善幅度——需要标注数据集做 A/B/C 对比实验，这是我们的下一阶段，不预先编造数字。

**Q8. 算法创新与开源复用怎么区分？**
复用：MediaPipe 关键点模型、OpenCV 采集——公开库，NOTICE 里有完整许可清单。我们的工作：五个姿态特征的几何定义与缺失语义、八态时序状态机与滞回参数体系、个人基线 z 分数判定与低方差兜底、提醒冷却/延后/反馈闭环、A/B/C 评估框架与事件匹配规则，以及整体产品化。每一行都在仓库里可审。

**Q9. 如何证明系统有效？**
分三层：软件正确性——180 项自动化测试全部通过，现场 4 秒可重跑；运行真实性——冒烟自检真实开摄像头推理并写结果文件；算法效果——需要标注数据，我们已实现评估框架（事件 IoU≥0.3 匹配、P/R/F1/误报率/延迟），但**目前没有实验数字**，这是诚实边界。

**Q10. 测试集怎么构建？**
方案已定（annotations.py 支持 JSONL 标注）：录制多段真实使用视频，人工标注"持续异常姿态"的起止区间，不确定样本单独列表不计入 P/R；调参集与测试集分离。缺口是执行——标注耗时，列为下一阶段第一项。

**Q11. 如何评估误报与漏报？**
事件级而非帧级：预测事件与标注事件时间重叠 IoU≥0.3 且起点误差 ≤2 秒算匹配，贪心一对一。指标：Precision/Recall/F1、FPR、每小时误报次数、平均检测延迟。evaluation.py 有 17 项测试验证这些计算本身正确。

**Q12. 摄像头角度有什么影响？**
影响很大，我们正视它：所有特征是二维图像几何量，摄像头俯仰/偏航/距离都会改变数值——README 和 UI 都明示。缓解手段：个人基线在用户自己的摄像头条件下校准，把"安装差异"吸收进 μ 和 σ；滑窗与持续时间判断吸收残余波动。不同机位间的绝对角度比较我们不支持，也不声称支持。

**Q13. 系统保存原始视频吗？**
不保存。数据库四张表（会话/事件/反馈/基线）只存时间戳、特征统计和状态元数据，schema 里没有任何图像或视频字段；画面在内存中即时处理即弃。隐私页可一键删除全部本地数据，删除动作有自动化测试。

**Q14. 当前版本有哪些局限？**
如实列四点：一，默认阈值是待标定初值；二，个人基线效果未经标注数据验证；三，提醒投递目前只有状态栏消息，toast/声音未实现；四，只支持摄像头实时输入，暂不支持视频文件分析；五，二维特征对摄像头摆放敏感。这些都在 README 与 PPT 里写明。

**Q15. 下一阶段怎么改进？**
按优先级：采集标注数据并跑 A/B/C 对比实验（框架已就绪）→ 用实验结果标定阈值 → 完善提醒投递（toast/声音）→ 视频文件输入 → 扩充不同光照/机位的鲁棒性测试 → 打磨安装部署体验。

**Q16. 为什么符合竞赛方向？**
（按所报赛道选择表述，通用版）项目把计算机视觉技术落到一个真实、高频的日常场景，完成了从算法、产品到验证体系的完整闭环，并且坚持可复核的工程诚信：所有性能数字有来源，所有未验证项如实标注。创新点是个性化基线、时序判断与可解释闭环的系统整合。

**Q17. 性能能不能支撑实时？**
实测两个数据点：开发期 640×480 下 30 FPS、单帧 31 毫秒（核显笔记本，纯 CPU）；冒烟自检在默认 1280×720 下录得约 10.5 FPS、132 毫秒——后者包含摄像头遮挡下的全帧推理。MediaPipe lite 模型本身为 CPU 实时设计；若需更高帧率，降分辨率即可，分辨率是启动参数。
